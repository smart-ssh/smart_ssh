# Spec 0031 — Erststart-Hinweis (Verantwortung und Datenbank-Verschlüsselung)

Status: umgesetzt
Zweck: Vor der ersten Server-Verbindung bestätigt der Nutzer einmalig, dass er die Verantwortung für jedes bestätigte Kommando trägt und wie die lokalen Daten geschützt sind.
Bezüge: Spec 0024 (Sprache, lokale Einstellungen), Spec 0101 (Datenbank-Verschlüsselung), Spec 0028 (MCP-Verbindungen), Spec 0045 (Erweiterungen des Hinweises), ADR 0123 (Fehlergrenze für Erweiterungen).

## 1. Ziel

Beim allerersten Verbindungsaufbau zeigt die App einen Zustimmungs-Screen mit
zwei inhaltlichen Punkten in einem gemeinsamen Dialog (statt zweier
nacheinander wegzuklickender Popups):

1. **Verantwortung**: Die KI schlägt Kommandos vor, aber der Nutzer trägt die
   Verantwortung für jedes bestätigte Kommando.
2. **Datenbank**: Die lokale Datenbank ist verschlüsselt; den Schlüssel
   verwahrt der Schlüsselbund des Betriebssystems oder, falls eingerichtet, das
   Master-Passwort. Wer Zugriff auf das entsperrte Benutzerkonto hat, kann die
   Daten lesen (Spec 0101).

Der Screen ist ein Transparenz- und Bewusstseins-Instrument. Er leistet bewusst
nur die Verantwortungszuweisung an den Nutzer, keinen juristischen
Haftungsausschluss; der gehört in Lizenz- und Nutzungsdokumente.

## 2. Anzeigebedingung

Der Screen erscheint **einmalig**, danach nie wieder. Die Bestätigung wird
dauerhaft in den lokalen App-Einstellungen gespeichert (Muster wie die
Sprachwahl, Spec 0024), nicht in der Datenbank. Standard ist „nicht bestätigt".
Es gibt keine Oberfläche, um den Hinweis zurückzusetzen.

## 3. Inhalt

Der Text erscheint in der UI-Sprache (Spec 0024).

**Deutsch:**

```
Bevor es losgeht

Smart SSH schlägt dir Kommandos vor, die eine KI basierend auf deinen
Anfragen generiert. Nichts wird ausgeführt, ohne dass du es bestätigst —
außer du hast das über eigene Regeln bewusst anders eingestellt. Die
Verantwortung für jedes bestätigte Kommando liegt bei dir.

Die lokale Datenbank ist verschlüsselt. Den Schlüssel verwahrt der
Schlüsselbund deines Betriebssystems oder – wenn du es einrichtest – dein
Master-Passwort. Wer Zugriff auf dein entsperrtes Benutzerkonto hat, kann die
Daten lesen.

[ ] Ich habe das gelesen und verstanden.
              [Weiter]
```

**Englisch:**

```
Before you start

Smart SSH proposes commands generated by an AI based on your requests.
Nothing runs without your confirmation — unless you've explicitly set up a
rule that allows it. You're responsible for every command you approve.

The local database is encrypted. Your operating system's keychain holds the
key — or, if you set one up, your master password does. Anyone with access to
your unlocked user account can read the data.

[ ] I've read and understood this.
              [Continue]
```

## 4. Verhalten

- „Weiter" bleibt deaktiviert, bis die Checkbox aktiv ist. Der Dialog hat keinen
  Abbrechen- oder Schließen-Knopf; reines Wegklicken ohne bewusste Bestätigung
  ist nicht möglich.
- Der Screen erscheint, wenn der Nutzer einen Server zum Verbinden wählt und der
  Hinweis noch nicht bestätigt ist (auch beim lokalen Pseudo-Server). Er sperrt
  nur den Verbindungsaufbau, nicht die übrige App-Nutzung — Einstellungen, etwa
  die Provider-Konfiguration, bleiben vorher möglich. Wählt der Nutzer einen
  Server, zu dem bereits ein Tab offen ist, wird nur zu diesem Tab gewechselt.
- Nach „Weiter" wird die Bestätigung gespeichert; erst danach gilt der Hinweis
  als bestätigt und die ursprünglich gewählte Verbindung wird aufgebaut. Der
  Screen erscheint bei künftigen Starts nicht mehr.
- Schlägt das Speichern fehl, erscheint eine Fehlermeldung, es wird nicht
  verbunden, und der Hinweis gilt weiter als nicht bestätigt; er erscheint beim
  nächsten Verbindungsversuch erneut.
- Die Sperre wird zusätzlich **im Kern durchgesetzt**: Ein Verbindungsaufbau
  scheitert mit dem Code `FIRST_RUN_NOTICE_NOT_ACKNOWLEDGED`, solange der Hinweis
  nicht bestätigt ist — für jeden Aufrufer gleichermaßen, auch für
  automatische Verbindungen durch den MCP-Server (Spec 0028) und für einen
  Aufruf, der die Oberfläche umgeht. Ist der gespeicherte Zustand nicht lesbar
  oder fehlt er, gilt der Hinweis als nicht bestätigt, nie als bestätigt.

## 5. Grenzen

- Es gibt keine Oberfläche, um den Hinweis nachträglich erneut anzuzeigen.

## 6. Optionale Erweiterungen

Editionen, die auf dem Kern aufbauen, können dem Hinweis eigene, optionale
Inhalte hinzufügen (z. B. zusätzliche Checkboxen oder Felder), ohne den
Kern-Hinweis zu ändern (Spec 0045).

- **Ohne Erweiterung** sieht der Hinweis genau so aus und verhält sich genau
  so wie in den Abschnitten 3 und 4 beschrieben.
- **Platzierung:** Jede Erweiterung erscheint in einem eigenen, optisch
  abgesetzten Bereich unterhalb der Pflicht-Bestätigung. Mehrere Erweiterungen
  erscheinen in ihrer festgelegten Reihenfolge.
- **Pflichtteil unantastbar:** Eine Erweiterung sieht und ändert weder den
  Hinweistext noch die Pflicht-Checkbox noch, ob „Weiter" aktiv ist. „Weiter"
  hängt allein von der Pflicht-Checkbox ab. Eine Erweiterung kann die
  Bestätigung weder überspringen noch vorab setzen.
- **Voreinstellung:** Jedes optionale Element einer Erweiterung ist beim Anzeigen
  aus bzw. leer. Nichts ist vorausgewählt.
- **Bei „Weiter":** Erst wird die Pflicht-Bestätigung gespeichert. Nur wenn das
  gelingt, wird danach jede Erweiterung genau einmal benachrichtigt. Schlägt das
  Speichern fehl, wird keine Erweiterung benachrichtigt (Verhalten wie in
  Abschnitt 4).
- **Fehler einer Erweiterung:** Scheitert eine Erweiterung bei dieser
  Benachrichtigung, wird das protokolliert. Die Bestätigung bleibt gespeichert,
  der Hinweis schließt sich, die übrigen Erweiterungen werden trotzdem
  benachrichtigt und die Verbindung wird wie gewohnt aufgebaut. Scheitert eine
  Erweiterung schon beim Anzeigen (oder später, solange der Hinweis offen ist),
  wird das mit ihrer Kennung protokolliert und ihr Bereich verschwindet
  vollständig, ohne leeren Rahmen. Hinweistext, Pflicht-Checkbox, „Weiter" und
  alle übrigen Erweiterungen bleiben bedienbar; der Hinweis lässt sich also
  weiterhin bestätigen. Eine so gescheiterte Erweiterung wird bei „Weiter" nicht
  benachrichtigt, die übrigen genau einmal wie oben beschrieben.
